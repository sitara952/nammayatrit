# General State Management Patterns

This document describes the primary state management patterns used in the application, focusing on Redux Toolkit for global client state and React Query for server state.

## Overview

*   The application employs a combination of state management solutions:
    *   **Redux Toolkit:** For managing global, client-side application state that needs to be shared across various parts of the app (e.g., user session, ongoing journey details, app settings).
    *   **React Query:** For managing server state, including data fetching, caching, synchronization, and updates with optimistic updates.
    *   **Local Component State (`useState`, `useReducer`):** For UI-specific state that doesn't need to be shared globally or persisted beyond the component's lifecycle. This is typically managed within Flow files/hooks.

## Redux Toolkit Pattern

*   **Setup:** Redux is configured using Redux Toolkit, likely with a store setup in `src/typescript/state/store.ts` (or a similar location).
*   **Slices:** State is organized into "slices" (e.g., `journeySlice.ts`, `sessionSlice.ts`, `userSlice.ts`), typically located in `src/typescript/state/client/` or feature-specific state directories. Each slice defines its reducers and actions.
*   **State Access (Reading):**
    *   **Selectors:** Always use dedicated selector functions exported from slices to read data from the Redux store (e.g., `selectJourneyLegs(state, journeyId)`, `selectCurrentLocation(state)`).
    *   Selectors are used with the `useAppSelector` hook (a typed version of `useSelector`) within Flow files/hooks or components that need to subscribe to state changes.
    *   **Avoid Direct State Path Access:** Do not access state directly via object paths (e.g., `state.journey.journeys[id].legsStatus`) outside of the slice itself. Selectors provide abstraction, memoization capabilities, and make refactoring easier.
*   **State Updates (Writing):**
    *   **Actions:** Actions are dispatched to update the state. Action creators are typically generated by `createSlice` from Redux Toolkit.
    *   **`useAppDispatch`:** The `useAppDispatch` hook (a typed version of `useDispatch`) is used in Flow files/hooks to get the dispatch function.
    *   **Reducers:** Reducers within slices handle these actions to produce new state immutably.
*   **Immutability:** Redux Toolkit's `createSlice` uses Immer internally, allowing "mutable" syntax within reducers while ensuring actual state updates are immutable.

## React Query Pattern

*   **Purpose:** Used for fetching, caching, synchronizing, and updating server state. It significantly simplifies data fetching logic and provides features like automatic refetching, pagination, infinite scrolling, and optimistic updates.
*   **Hooks:**
    *   `useQuery`: For fetching data (GET requests).
    *   `useMutation`: For creating, updating, or deleting data (POST, PUT, DELETE requests).
*   **Query Keys:** Unique keys are used to identify and manage queries. These keys are crucial for caching, refetching, and invalidating data.
*   **Location of Logic:** React Query hooks (`useQuery`, `useMutation`) are primarily used within:
    *   Flow files/hooks associated with screens that need server data.
    *   Custom hooks that encapsulate specific data fetching logic for a feature or entity.
*   **API Service Functions:** React Query typically calls asynchronous functions (API service functions) that handle the actual HTTP requests. These service functions are often defined in `src/typescript/api/` or feature-specific API utility files.
*   **Server State vs. Global Client State:**
    *   Data fetched from the server and managed by React Query should generally be considered server state.
    *   If parts of this server state also need to be reflected in the global Redux store for wider, synchronous access by other parts of the app, this synchronization must be handled explicitly (e.g., by dispatching a Redux action in the `onSuccess` callback of a `useQuery` or `useMutation`). However, prefer deriving state or passing data via props where possible before duplicating server state into Redux.

## Utility Hook Pattern (for State and Logic Encapsulation)

*   Specialized custom hooks (e.g., `usePublicTransportUtils`, `useRiderLocation` found in `src-v2/multimodal/utils` or `src-v2/multimodal/hooks`) are used to encapsulate specific domains of logic, data fetching (which might involve React Query or direct access to non-Redux caches like `globalCache`), and state management.
*   These hooks often provide both utility functions and relevant data directly to their consumers (other hooks or Flow files).
*   **Consumption:** Feature-specific hooks or UI components should prefer consuming these utility hooks for their data and functionalities rather than reimplementing logic or directly accessing underlying data sources managed by these utility hooks.
    *   Example: `useRiderLocation` might manage fetching and updating the rider's location (potentially updating Redux as a side effect) and directly returns `latLong`. Consumers should use this returned `latLong`.
*   This pattern promotes modularity, reusability, and hides the complexity of underlying data sources or state mechanisms.

## Choosing the Right State Management Tool

*   **Local State (`useState`/`useReducer` in Flow files):** For data that is only relevant to a single screen/component and doesn't need to be shared or persist.
*   **Redux Toolkit:** For global client-side state that is shared across many unrelated parts of the application, or state that needs to be persisted and rehydrated.
*   **React Query:** For any data that comes from or is sent to a server. It handles caching, background updates, and optimistic updates effectively.
