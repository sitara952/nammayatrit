# Ride Booking: Search Patterns

This document outlines system patterns related to the ride search and selection phase, primarily based on the implementation in `src-v2/screens/Search/Flow.tsx`.

## Search Flow & State Management (`Search/Flow.tsx`)

The search process is managed within the `SearchModalFlow` component (in `Search/Flow.tsx`) and heavily relies on Redux for state.

1.  **Input State (Redux):**
    *   User input for source and destination(s) is stored in Redux state using selectors like `selectStartLocationFromTextInput`, `selectSeletedStopLocationsTextInput` (from the `session` slice).
    *   `selectActiveInput` determines which field (source/destination) is currently being edited.
    *   Selected location objects (after parsing and serviceability checks) are stored via `selectSearchedSource` and `selectSearchedStops`.
2.  **Location Predictions (Autocomplete):**
    *   The `useLocationPredictions` custom hook is employed to fetch autocomplete suggestions as the user types.
    *   Input to this hook is debounced using `lodash.debounce` (typically 500ms) to optimize API calls for predictions.
    *   Prediction requests are biased using `currentLocationCoords` or `lastKnownLocation` (from Redux state) to provide relevant suggestions.
    *   The `searchData` (results from `useLocationPredictions`) is passed to the UI component for rendering.
3.  **Location Selection & Processing (`handleCardPress`, `getParsedLocation`):**
    *   When a user selects a predicted location from the UI:
        *   Haptic feedback (`hapticEffect`) is triggered for better UX.
        *   The `getParsedLocation` function is invoked:
            *   If the selected item lacks a `placeId`, it's considered pre-enriched and used directly.
            *   Otherwise, it calls `GetLocationAndServiceability.getLocationObjectAndServiceability` (a ReScript utility from `LocationUtils.bs`). This function takes a payload generated by `getPlaceNameAPIBody` and fetches detailed place information, including its serviceability status. This is a key point of interaction with ReScript helper modules.
            *   The serviceability status (`parsedData.serviceable`) is dispatched to Redux using `setIsServiceable`.
            *   The enriched location object (including `tag: 'RECENTS'`) is dispatched to update `searchedSource` or `searchedStops` in Redux via `setSearchedSource` or `updateSelectedSearchedStop`.
            *   If the location is serviceable, it's cached as a recent search using `LocationObjectCaching.setRecentSearches` (another ReScript utility).
4.  **Serviceability Checks & Flow Control:**
    *   After a location is parsed and its serviceability is determined:
        *   **Source Selection (`handleSourceCardClick`):** If the selected source is serviceable and all destination stops (if any) are also filled and serviceable (checked by `checkServiceAndNullStopsOnSourceClick`), the flow proceeds by calling `setDropGateAndNavigate`. Otherwise, focus might be directed to an incomplete/unserviceable destination input.
        *   **Destination Selection (`handleDestinationCardClick`):** If the source is not yet set or is unserviceable, focus is shifted back to the source input. If any intermediate stops are null or unserviceable, `onStopUnserviceable` is called, which focuses the problematic input field. `checkServiceAndNullStopsOnDestinationClick` validates this. If all valid, `setDropGateAndNavigate` is called.
5.  **Navigation to Next Stage (`setDropGateAndNavigate`):**
    *   If all selected locations are valid and serviceable:
        *   The `useCheckForInterCity` hook determines if the trip is inter-city based on the source and stops.
        *   If `isInterCity` is true for a destination, the `bottomSheetStage` in Redux is set to `BottomSheetStage.IntercitySearchDetails`.
        *   Otherwise, it checks if the location has special "Drop" only gates (`parsedData.specialLocation?.gatesInfo`). Based on this, `isPickup` state (Redux) is set, and `bottomSheetStage` is set to `BottomSheetStage.ConfirmPickup`.
6.  **Multimodal Transit Preferences:**
    *   The `SearchModalFlow` component accepts an `isMultimodal` prop.
    *   If `isMultimodal` is true, the UI allows users to select preferred transit modes (bus, metro, train) and specific bus routes (e.g., 'ordinary', 'deluxe') via `editTransitValues`.
    *   This state is managed locally within `Search/Flow.tsx` using `useState` (`transit`, `setTransit`) and relevant handlers (`handleTransitSwitchChange`, `handleBusRoutePress`).
7.  **Back Navigation & Reset (`handleOnPressBack`):**
    *   Resets the `bottomSheetStage` in Redux to `BottomSheetStage.Home`.
    *   Dispatches `clearSession` to clear specific Redux states like `currentLocation`.
    *   Calls `resetIds` (a shared reducer utility).
    *   Resets `searchedSource` to an initial `props.sourceData` (if provided).
    *   Handles navigation based on an `originTab` route parameter (e.g., navigating back to 'live' tab).

## Map Integration for Search

*   **Displaying Search Area & Options:** While `Search/Flow.tsx` manages the data and logic, the corresponding `Search/UI.tsx` would be responsible for rendering map elements.
*   **Pattern:** The general **Map Integration Pattern** (detailed in `memory-bank/systemPatterns_general/uiArchitecture.md`) is expected to be applied in `Search/UI.tsx`:
    *   Use of the `MapProvider` component.
    *   Providing `initialCoordinate` based on user's current location or search input.
    *   Overlaying search input fields, location pickers, and markers for ride options on the map.
*   **Key Components (in UI):**
    *   `MapView` (from `react-native-maps` via `MapProvider`).
    *   Custom markers for pickup/drop-off points.
    *   Address search input components.

## Key Technical Decisions / Patterns Evident in `Search/Flow.tsx`

*   **UI/Flow Separation:** `SearchModalFlow` (logic) provides props (`searchModalViewState`) to `SearchModalView` (UI).
*   **Redux for Core Search State:** Manages input values, selected locations, active input field, serviceability flags, and UI state like `bottomSheetStage`.
*   **Custom Hooks for Encapsulated Logic:**
    *   `useLocationPredictions`: Handles autocomplete API interactions.
    *   `useCheckForInterCity`: Determines if a trip is inter-city.
*   **ReScript Bridge for Core Utilities:** Leverages ReScript helper modules (`LocationUtils.bs`, `LocationObjectCaching.bs`) for critical location processing, serviceability checks, and caching. This is a significant pattern of TypeScript-ReScript interoperation.
*   **Debouncing:** `lodash.debounce` optimizes calls to the location prediction service.
*   **Programmatic Focus Management:** `useRefsContext` provides `TextInput` refs to programmatically focus fields based on validation or flow logic.
*   **Haptic Feedback:** `hapticEffect` from `react-native-haptic-feedback` enhances UX.
*   **Conditional Logic for Multimodal:** The flow adapts to include transit preferences if `isMultimodal` is true.

*(The direct use of React Query for managing the state of location predictions is not explicit in `Search/Flow.tsx` itself; it's likely encapsulated within `useLocationPredictions` or related API service layers. The primary state management pattern visible for search UI state in this file is Redux.)*

## Pickup/Drop-off Confirmation Patterns (`ConfirmPickup/Flow.tsx`)

After an initial location is selected in the Search flow, the `ConfirmPickup` screen allows users to refine and confirm the exact pickup or drop-off point, often by interacting with a map.

1.  **Initialization & Context:**
    *   The `ConfirmPickup` flow receives `isPickup` (boolean from Redux `session` slice) to determine if it's confirming a source or destination.
    *   It uses `MapContext` for `mapRef` and `useConfigContext` for theme colors.
    *   Redux state for `searchedSource`, `selectedSearchedStop`, `currentLocation`, and map state (`isMapMoved`, `currentRegion` from `maps` slice) are crucial.
2.  **Map Interaction for Precise Pinning:**
    *   A central marker (`AnimatedPickupMarker`) on the map indicates the point being selected.
    *   As the user moves the map (`reduxCurrentRegion.isGesture` is true):
        *   A polyline may be drawn from `currentLocation` to map center (Android, short distances).
        *   `getAsyncSourceLocation` is called (debounced or on gesture end) to fetch location details for the map's center using `GetLocationAndServiceability.getLocationObjectAndServiceability` (ReScript util).
    *   The fetched `regionLocation` updates the corresponding Redux state (`searchedSource` or `selectedSearchedStop`).
3.  **Handling Special Locations (Gates/Zones):**
    *   If the initial location (`source` or `selectedStop`) has `specialLocation` data:
        *   `extractAndTransformLocations` and `transformSpecialLocationToLocation` (ReScript util) prepare gate data.
        *   `handleSpecialLocationOnMap` (from `ConfirmPickupUtils`) displays gates/zones on the map.
        *   Users can click on a gate (`handleMarkerClick`, `handleSpecialLocClick`), updating `selectedGateId` state.
        *   The camera animates to the selected gate, and Redux is updated with the gate's specific coordinates.
        *   Supports a "custom pickup zone" if the location type is 'Open' and the pinned location is valid within it.
4.  **Handling Hotspots:**
    *   If a location has `hotSpotInfo` (and is not a special location):
        *   `handleHotspotLocationsOnMap` (from `ConfirmPickupUtils`) displays hotspots.
        *   `findNearestHotspot` can auto-select the nearest one.
        *   Clicking a hotspot (`handleHotspotClick`) animates the camera and fetches location details for it.
5.  **Pickup Distance Validation:**
    *   If confirming a pickup (`isPickup` is true), `haversineDistance` calculates the distance between the confirmed `source` and `currentLocation`.
    *   `isPickupTooFar` state is set if it exceeds `PICKUP_DISTANCE_THRESHOLD_IN_M`, which can be shown in the UI.
6.  **Editing Selected Location:**
    *   Users can click on the displayed source/destination text (`onClickSource`, `onClickDestination`, `handleLocationClick`) to return to the `Search` bottom sheet stage (`BottomSheetStage.Search`) to pick a different general location.
7.  **Final Confirmation (Implied):**
    *   While this `Flow.tsx` focuses on refining the pin, the actual "Confirm" button action that proceeds to the next stage (e.g., fetching ride options or payment) would be handled by the UI component, likely dispatching an action that this Flow or a parent orchestrator would handle to move to `LookingForRides` or a similar state.
8.  **Map Padding & Camera:**
    *   Dynamic map padding (`addStaticMapPadding`) is applied, possibly to account for UI elements like bottom sheets.
    *   `animateCameraToLocateOnMap` initializes the map view.
    *   `DEFAULT_CAMERA_ZOOM_CONFIRM_PICKUP` is used.

### Key Technical Aspects for Confirmation:
*   **Heavy Map Interaction:** Relies on `MapContext` and direct `mapRef` manipulations for camera animations, adding/removing markers, zones, and polylines.
*   **Redux for State:** Manages the precise location being confirmed, UI mode (`isPickup`), and map interaction state.
*   **ReScript Utilities:** Continues to use `LocationUtils.bs` for fetching location details based on map coordinates.
*   **Utils for Complex Logic:** `ConfirmPickupUtils.ts` contains significant helper functions for special location and hotspot handling.
